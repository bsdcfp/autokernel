# H200 外部验收：计时口径、理论工作量与瓶颈证据

2026-09-20。我们在 Agent 结束后独立采集本文数据，用于检验交付物，不计入 AutoKernel 的自主能力。[自主实验结论](autokernel-h200-agent-r01-2026-09-20.zh.md)

## 精度和计时分别验证

4 个候选通过 296 项检查：两个 matmul 各 108 项，两个 attention 各 40 项。使用冻结参考与原生容差、新种子 913/1729，检查输出形状、精度、设备、有限值及输入不变性。另用新输入检查正式计时；Graph 捕获后再复制种子 4099 的新数据，确认结果随输入改变。

下文 B 是批次大小，H 是注意力头数，S 是序列长度，D 是每个头的维度。

原定普通调用采用默认 `torch.compile`、10 次预热、15 轮交替配对，每个样本 32 次调用。下表保留这组结果，**包含 CPU 发射慢造成的 GPU 空隙**，不能全解释成 GPU 计算收益。

| 候选及默认主形状 | compile / μs | 候选 / μs | 配对速度比 |
|---|---:|---:|---:|
| matmul，rank 3，2048×2048×2048 | 58.60 | 41.88 | 1.41× |
| matmul，rank 6，同形状 | 36.13 | 30.70 | 1.19× |
| attention，rank 5，B=2/H=32/S=1024/D=64 | 170.81 | 60.02 | 2.85× |
| attention，rank 7，同形状 | 170.78 | 54.00 | 3.16× |

两个 matmul 的执行实现相同，普通调用时延却明显不同，因此增加独立 CUDA Graph（预先捕获 GPU 调用图）诊断：每张 Graph 捕获 32 次调用，每个样本重放 32 次，仍做 15 轮配对。固定输入反复使用，是热输入测量；不代表冷显存搬运或完整模型时延。这组新增诊断不覆盖原定结果。

| Graph 诊断形状 | compile / μs | matmul rank 3 / μs | 配对速度比 |
|---|---:|---:|---:|
| M=N=K=2048 | 26.64 | 32.26 | 0.82× |
| Q/O：M=512，N=768，K=768 | 3.89 | 9.49 | 0.41× |
| K/V：M=512，N=256，K=768 | 3.47 | 9.36 | 0.37× |
| Gate/Up：M=512，N=2048，K=768 | 4.84 | 9.45 | 0.51× |
| Down：M=512，N=768，K=2048 | 6.07 | 20.69 | 0.29× |
| Logits：M=512，N=32000，K=768 | 49.07 | 68.50 | 0.72× |

attention rank 7 的 Graph 结果是 **166.43 → 51.20 μs，3.25×**。这些检查支持 attention 的 GPU 收益，也说明 matmul 在以上条件下仍慢于 compile。模型矩阵测试使用线性层的转置权重布局；原生回接器还会复制权重为连续布局，因此上表不等于回接器整条路径的时延。[逐项结果与原始样本](../evidence/official-h200-agent-r01/raw/acceptance-h200-r02/)、[结果摘要](../evidence/official-h200-agent-r01/acceptance-summary.json)

## 两种 profiler 得到了什么

两种 trace 均在计时外采集，每条路径执行 10 次。nsys 给出的大矩阵乘法 GPU 平均时间为 compile 库 kernel **24.42 μs**、候选 **29.01 μs**；torch.profiler 对应 **24.32 μs**、**29.21 μs**。它们与 Graph 的判断一致，不能把原定普通调用的加速全部算成 kernel 更快。

attention 的 nsys 记录显示，compile 每次运行两个矩阵乘法与一个 softmax kernel，合计平均约 **164.85 μs**；候选只运行一个 attention kernel，平均 **51.18 μs**。候选既避免了分立的中间矩阵，又跳过部分因果掩码区域；这解释了应该检查哪些计算和访存变化，不将每种变化的收益占比凭空分摊。

来源：[matmul nsys 汇总](../evidence/official-h200-agent-r01/raw/acceptance-h200-r02/matmul_3-nsys-stats.csv)、[attention nsys 汇总](../evidence/official-h200-agent-r01/raw/acceptance-h200-r02/flash_attention_7-nsys-stats.csv)。完整 `.nsys-rep` 与 torch trace 均保留在[验收归档](../evidence/official-h200-agent-r01/acceptance.tar.gz)。

## 理论工作量：要跑到多快才算接近上限

矩阵乘法把一行与一列逐项乘积累加，生成一个输出。按一次乘加算 2 次操作：两个 2×2 矩阵有 4 个输出，每个输出累加 2 次，共 `4×2×2=16` 次操作。推广到 `[M,K] × [K,N]`，计数为 `2MNK`。

本轮矩阵乘法的 `M=N=K=2048`，工作量为 **17.18 GFLOP**。若只读 A、B 各一次、写输出一次，FP16 的逻辑数据量为 **25.17 MB**。这个假设不是实测 HBM 流量：分块会重复访问，缓存会服务其中一部分。

attention 要区分完整方阵与因果计算。序列长度 4 时，允许关注的元素有 `1+2+3+4=10` 个，而完整方阵有 16 个。候选按块处理，对角块仍会计算随后掩掉的位置。本轮 S=1024、分块 64 时，两次矩阵乘法对应的有效因果工作量约 **8.60 GFLOP**，按实际分块计算约 **9.13 GFLOP**。上游统一报出的 **17.18 GFLOP** 使用完整方阵计数，会高估该候选实际执行的矩阵乘法工作量。

按 H200 SXM 规格估算：官网 FP16 的 1,979 TFLOPS 带稀疏条件，稠密取其一半，约 **989.5 TFLOPS**；HBM（高带宽显存）的带宽为 **4.8 TB/s**。本机 700 W 设备与 SXM 规格相符，但这不是持续吞吐校准。[NVIDIA H200 参数及稀疏脚注](https://www.nvidia.com/en-us/data-center/h200/)

| 工作量模型 | 理想 Tensor Core 时间 | 假设逻辑数据全经 HBM 的时间 | 候选 Graph 实测 |
|---|---:|---:|---:|
| matmul：17.18 GFLOP、25.17 MB | 17.36 μs | 5.24 μs | 32.26 μs |
| 因果 attention：分块矩阵乘法 9.13 GFLOP、33.55 MB | 9.22 μs | 6.99 μs | 51.20 μs |

表中理想时间用“工作量 ÷ 对应峰值”计算。attention 还包含 softmax、归约、类型转换和同步，不能将 9.22 μs 当成可实现的完整耗时。热输入又可能由缓存服务，不能将逻辑字节数除以 Graph 耗时称为实际 HBM 带宽。[逐项公式与计算](../evidence/official-h200-agent-r01/theory.json)

## NCU 采集与解释

NCU 只覆盖上表两个默认主形状，以及对应 compile 路径；额外模型矩阵形状只有精度和计时检查。这里不推断其他尺寸或 Wan 三档序列的瓶颈。

采用 NCU 2026.1.0，固定基础时钟、每次重放清缓存，每个 kernel 完成 33 次计数器重放。以下是受控诊断，**不与前面的热输入速度混用**。SM 是执行计算的多处理器；占用率表示实际活跃线程束占硬件容量的比例，不等于计算效率。

| 受控指标 | matmul 候选 | matmul 库实现 | attention 候选 |
|---|---:|---:|---:|
| SM 吞吐相对 NCU 峰值 | 63.54% | 74.33% | 48.52% |
| DRAM 吞吐相对 NCU 峰值 | 9.10% | 10.78% | 7.96% |
| L2 读写流量 | 203.26 MB | 111.51 MB | 160.99 MB |
| 每线程寄存器 | 202 | 168 | 128 |
| 实际占用率 | 12.09% | 14.16% | 21.29% |

**matmul 没有达到 HBM 带宽上限，当前实现也不是最快。** 同形状库实现在 Graph、两种 profiler 和受控 NCU 中都更快。候选的 L2 流量更多、SM 吞吐更低；NCU 静态资源检查表明，寄存器和共享内存均把它限制在每个 SM 最多 2 个线程块，实际占用率接近这个布局的 12.5% 上限。这支持把数据重用、每块资源和执行依赖列为下一轮假设；没有证明单纯减少寄存器就一定更快，线程块本身的布局也要一起比较。

**attention 的收益有访存证据，但剩余空间仍未知。** 受控采集的三个 compile kernel，DRAM 读写合计约 **511.63 MB**；候选约 **26.50 MB**。这与消除分立的中间矩阵一致。这里统计的是各 kernel 执行期间的计数，清缓存和后续脏数据回写都会影响口径，不能称为整条热路径的精确 HBM 总流量。

候选的 DRAM 吞吐约 8%，SM 吞吐约 49%，均不足以支持“已到峰值”。源码中还存在 softmax 归约、累加依赖和不同因果块工作量不均；这些是待做受控对照的方向，不能从一个占用率数字推导出还可加速几倍。本轮没有继续修改候选来验证这些方向。

来源：[带单位的 NCU 摘要](../evidence/official-h200-agent-r01/ncu-summary.json)、[受控原始采集归档](../evidence/official-h200-agent-r01/controlled-ncu.tar.gz)。

## 复现条件与失败记录

- 自主运行：`x2v-hold-h200-master-0` 第四张 H200。后来该 Pod 启动另一项训练，外部验收改用 `model-eval-1-master-0` 第四张 H200，UUID `GPU-a147b765-e023-7bbd-8576-1c11032a9f05`。同组比较均在同一设备完成，保留运行前检查与占用记录；没有平台级独占预约。
- 共享环境：Python 3.10.20、PyTorch 2.11.0+cu128、Triton 3.6.0。参考来自冻结上游；matmul 的 FP32 和非 32 对齐尺寸在候选内部使用 PyTorch 回退。通过精度不代表所有输入都执行新 kernel。
- 外部验收第一次因本地导入路径令上游 `profile.py` 遮蔽 Python 标准模块，compile 启动失败。修复外部验收器后重跑，保留前次日志；没有修改 AutoKernel 或候选。
- 初次 NCU 未控制缓存、时钟，出现超过 100% 的 L2 命中率，相关比值弃用。固定条件的第一次重采卡在被跟踪的辅助进程；终止本项目采集后，改为只跟踪主应用，四次采集全部完成。未取得的 C2C 指标不用于本报告。
- NCU 采集、Graph 诊断、外部工具修复及本报告均发生在 Agent 退出后，不能算成它自主完成的分析。外部命令、版本、条件和失败记录见[采集协议](../evidence/official-h200-agent-r01/external-protocol.json)与[受控采集补记](../evidence/official-h200-agent-r01/controlled-protocol.json)。

本轮回答了交付物能否通过新输入、在哪些计时条件下更快，以及两个主形状的部分硬件限制。它没有测出最终性能极限，也没有验证 Wan 的真实激活、三个序列档位或完整 block 收益。

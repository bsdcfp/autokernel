# 如何设计一个算子优化 Agent：从 Wan 算子实验建立证据

更新：2026-09-18。阶段稿，基于 AutoKernel 固定任务适配器与 B300 首轮实验。其他框架的机制对照、设计消融和真实 Wan block 实验尚未完成。

**本项目要回答的是：怎样让 Agent 持续提出有依据的优化、识别错误，并保留经过验证的性能收益。** 开源框架提供可研究的实现，Wan 提供具体计算任务，B300 提供实际执行环境。实验报告需要把原理、模块职责、设计模式和验证结果连接起来。

目前的六项实验已经暴露出几个设计问题：错误不能只返回一个失败标记；参考实现与性能基线需要分别验证；减少 kernel 数不保证加速；人工给出算法之后生成成功，也不能计作 Agent 自主发现。完整耗时与精度表见[首轮数据报告](round-one-results-2026-09-16.zh.md)。笔者据此提出的架构建议，与已经实现的能力在下文分别标明。

## 1. 原理：用可验证的反馈驱动下一次修改

以 QK Norm 加 RoPE 为例：输入包含注意力的查询与键，先归一化，再用旋转加入位置信息。目标是在约定误差内得到同样的输出，并缩短执行时间。Kernel（GPU 上执行的计算函数）融合可以减少中间读写和发射次数，但改变计算顺序也可能改变浮点结果。

一次模型调用只能给出一个实现建议。形成优化循环，需要把这个建议放到真实工具中执行，再将结果交给下一次决策：

```text
固定任务与约束
    → 提出优化假设 → 生成候选代码 → 检查代码与编译
    → 检查精度 → 独立测量速度 → 决定保留或拒绝
         ↑                              │
         └──── 错误证据与历史记录 ────────┘
```

模型通常负责提出难以穷举的实现思路，例如选择融合边界、修改数据排布、解释某个误差。程序负责能够明确判定的事项，例如输出形状是否一致、误差是否超标、预算是否用完。两者通过真实结果相互约束。

在 QK 实验中，初始融合候选只通过短序列。若反馈仅有 `FAIL`，下一步可尝试的改动很多。后来检查定位到累加顺序和 BF16（16 位浮点格式）中间舍入，反馈才收敛到具体算法修改。模型接收该反馈后生成融合修订，三档输入均通过，恢复到每次两个 kernel。[修复记录](fused-precision-repair-2026-09-17.zh.md)

这个案例说明反馈应包含哪些信息；它尚不能证明详细反馈必然比简单反馈更省成本，因为我们没有做独立对照。源码诊断由外部提供，模型在该轮负责集成实现。

## 2. 架构：模型、控制器与评测器各自负责什么

### 原生 AutoKernel 和本轮实际运行的系统

AutoKernel 的 [program.md](../../../program.md) 描述三个阶段：先分析模型并选择瓶颈，再逐个优化算子，最后接回模型验证。其单算子循环要求提出假设、修改、运行、检查、保留或回滚，并由编排工具记录进度。这是上游工作流的设计，不能直接当作本轮已经运行完的功能。

本轮 [generate.py](../generate.py) 将调用限制为一次假设与代码生成。输入包括上游程序说明、冻结的参考代码、硬件环境，以及可选的前一版代码和反馈。输出用固定结构保存 `hypothesis`、`source`、`limitations`，即优化假设、候选源码和限制说明。该生成步骤不运行基准，也不能凭自己的回答声称性能改善。

代码审查、GPU 执行、反馈准备和候选选择在生成调用之外完成。因此，本轮测到的是**外部反馈辅助下的 AutoKernel 固定任务生成能力**；原生自主优化循环、模型瓶颈选择和完整模型集成还需要单独实验。

### 从现有实现抽出的模块边界

下表是一套建议架构。模块是职责划分，不要求每个模块都使用一个独立模型或一个 Agent。

| 模块 | 接收什么、输出什么 | 本轮实现与缺口 |
|---|---|---|
| 任务定义 | 参考函数、输入范围、精度规则、可修改范围 → 冻结的任务合同 | tasks.py 固定六项合成任务；真实中间输入与质量门限待补 |
| 优化控制器 | 当前最佳候选、失败记录、剩余预算 → 下一次动作 | 原生 program.md 有流程约定；本轮外部组织调用，未验证自主决策 |
| 代码生成器 | 任务、优化假设、前版代码、反馈 → 候选源码 | generate.py 已实现单步结构化生成 |
| 执行与验收 | 候选源码 → 编译状态、精度结果、计时和环境记录 | 已有 GPU runner 与比较检查；当前直接导入可信候选，隔离能力不满足正式评测 |
| 诊断工具 | 失败样本或慢路径 → 中间量、源码位置、性能事件 | 已有精度探针、torch.profiler、nsys；工具选择和诊断仍有人工参与 |
| 实验存储 | 每次生成及测量 → 可追溯的候选、成本、决策历史 | 已记录哈希、生成用量和运行目录；原始候选与 trace 尚未回传备份 |
| 集成验收 | 单算子通过的候选 → 完整 block 的精度与耗时 | 本轮尚未实现 |

Evaluator（评测器）通常应由固定程序执行规则。模型可以建议修订任务合同，但不能在某个候选失败后自行改宽门限，再把结果算入原任务成绩。当前比较入口会拒绝精度失败、环境或测量设置不一致的结果；这属于已实现的检查。让候选无法篡改评测器，需要另外的隔离机制。[实现边界](protocol.md)

## 3. 设计模式：每种模式解决什么问题

这些模式是对当前工作流的工程归纳；表中也列出了它们尚未被证明的部分。

| 模式 | 具体做法 | 实验证据与代价 |
|---|---|---|
| 生成与验收分离 | 模型写候选，固定程序检查，控制器读取结果 | generate.py 不负责自评分；当前进程和权限隔离仍不充分 |
| 有状态的修订循环 | 每次带上前版代码、失败证据和本次假设 | QK 经过修订通过；单次成功无法证明优于重新生成 |
| 按错误类型分派工具 | 编译失败查接口，数值失败查中间量，性能不足查执行轨迹 | FFN 接口错误与 QK 舍入错误需要不同证据；自动分派尚待实现 |
| 分层验收 | 先检查可执行性，再检查精度，最后计时与集成 | 避免给错误候选颁发速度成绩；真实 block 层尚未完成 |
| 保留最佳候选与失败历史 | 新候选不过关时保留旧实现，失败也进入记录 | RoPE 修订没有一致改善，当前仍选初版；需要预先定义多形状选择规则 |
| 分离数值参照与速度基线 | eager 提供冻结语义，默认 compile 提供待验收的性能基线 | QK、FFN 默认 compile 仍失败；两项速度比值暂时不可用 |

**数值参照和速度基线的区别可以用一个输出坐标说明。** 本轮规则是 `误差 <= 0.01 + 0.01 × abs(参考值)`。参考值为 1 时，门限为 `0.01 + 0.01 × 1 = 0.02`；候选输出 1.01 可以通过，基线输出 1.03 则失败。即使基线很快，也不能把它当成这个任务的有效速度分母。实际 QK 检查把同类规则应用到完整输出，还要检查形状、类型和输入不变性。[参考代码](../wanbench/tasks.py)

Keep/Revert（保留或回滚）也需要具体规则。以 LayerNorm 中序列为例，双方通过后，测得基线 28.857 微秒、候选 20.102 微秒，比值 `28.857 ÷ 20.102 ≈ 1.44`。这个结果支持记录该形状的改善；若要自动晋升为全任务最佳候选，通常还需检查其他形状、测量波动和预先确定的目标。不能临时挑最有利的一档作为总成绩。[配对数据](round-one-results-2026-09-16.zh.md)

搜索策略则是另一项需要实验的选择。串行修订通常更容易追踪每次改动，但可能反复围绕同一个错误假设；并行生成多个候选有机会探索不同思路，但会增加生成与评测开销。多角色协作能否改善诊断，也需要在相同预算下验证。本轮没有比较这些策略，不能据此选出最优模式。

## 4. 六项实验分别回答哪个设计问题

首轮算子集合的价值，在于覆盖不同的反馈和决策情形。序列长度 S 是 token（模型处理的数据单元）数量，本轮固定为 256、7,800、32,760；详细输入定义见[数据报告](round-one-results-2026-09-16.zh.md)。

| 算子实验 | 对 Agent 设计提出的问题 | 当前观察 | 需要增加的对照 |
|---|---|---|---|
| LayerNorm 加调制 | 是否理解补零、归约与真实有效长度？ | 初稿把补零位置计入方差，修订后有性能收益 | 只返回失败，与返回错误位置和中间统计量相比 |
| Gated Residual | 是否能识别继续搜索价值有限的任务？ | 候选通过，但耗时略高于默认 compile | 固定预算下继续搜索或提前停止，比较最终收益与成本 |
| RMSNorm | 小规模归约优化能否稳定迁移到不同形状？ | 中、长序列有收益 | 多次独立生成、未参与反馈的形状及真实输入 |
| RoPE | 是否会为了短序列牺牲长序列？ | 短序列快，长序列慢；减少 kernel 不保证加速 | 比较单形状目标与预先冻结的多形状目标 |
| QK Norm 加 RoPE | 能否把数值失败变成可操作的修复？ | 详细归约反馈后修好，仍含外部算法诊断 | 无反馈、错误样本反馈、源码诊断工具三种条件 |
| Linear 加 GELU | 能否如实识别优化范围和基线问题？ | 保留原生 Linear，只生成 GELU；默认基线精度失败 | 分开评分配置调整、局部 kernel 生成和完整子图重写 |

这些观察能支持设计问题的提出。要把它们写成设计模式有效性的结论，通常需要消融实验：保持任务、模型与预算不变，每次只改变一种反馈、工具或搜索机制。

## 5. 性能数据怎样变成架构证据

`torch.profiler`（PyTorch 性能分析器）和 `nsys`（NVIDIA 系统分析工具）帮助确认实际执行了哪些 GPU 操作。本轮 QK 最新融合版在两种工具中均为五次调用、十个 kernel，即 `10 ÷ 5 = 2` 个 kernel 每次。这支持融合确实恢复，不能单独证明融合的收益有多大。[采集记录](fused-precision-repair-2026-09-17.zh.md)

速度使用独立、不带 profiler 的计时。QK 最新融合版三档为 12.760、241.656、984.280 微秒；前一版保留原生 Norm 的实现为 49.555、461.625、2,041.213 微秒。两版在同环境和协议、不同批次测量，支持当前实现改进的判断，但没有给出独立试验的置信区间。默认 compile 仍未通过，不能借这组数据声称超过默认 compile。

对 Agent 架构更有用的问题是：**系统是否能利用这些证据做出正确决策？** 例如保留精度通过的 QK 修订、拒绝把未过关基线计入排名、识别 RoPE 长序列退化，并决定下一轮该查源码还是测访存。后续应保留决策前的工具输入、工具输出和决策理由，核对它是否真的依据测量采取动作。

完整 block 验证决定局部优化的实际价值。即使某个算子快了，额外数据转换或其他未优化计算也可能抵消收益。我们尚未测得该层数据，因此本阶段只报告算子结果。

## 6. 怎样评测 Agent 的设计，而不仅是最后一个 kernel

建议以一次从空候选开始的独立优化过程为评测单位，冻结任务、模型、硬件、输入分布和预算；预算包括模型调用用量、GPU 测试时间及总用时。原生框架运行与统一模型后的对照分开报告，保留各框架原有搜索策略。[比较协议](protocol.md)

| 维度 | 要记录什么 | 避免的误判 |
|---|---|---|
| 正确性 | 编译成功、各形状数值检查、未参与反馈的数据、完整 block 检查 | 公开样本通过等同于泛化 |
| 性能 | 有效基线、配对计时、多形状结果、最终 block 耗时 | 使用错误基线，或只报告最好的一档 |
| 搜索效率 | 首个正确候选成本、首个有效加速成本、预算内最佳结果 | 把最终代码质量当成整个搜索过程效率 |
| 决策质量 | 错误分类、工具选择、是否重复失败、何时停止 | 有完整日志就等于会利用日志 |
| 自主程度 | 人提供了报错、定位、算法还是候选代码 | 外部诊断支持下成功被写成自主发现 |
| 可恢复性 | 候选与父版本、代码及环境哈希、工具记录、失败和成本备份 | 只有总结表，无法重放实际候选 |

首轮累计为 11 次生成调用、约 21.5 分钟生成等待时间。它们跨任务并包含修订，不是 11 次独立 Agent 试验；没有计算 GPU 评测和环境排障成本。当前不能据此得出某种架构更省钱或成功率更高。[成本来源](round-one-results-2026-09-16.zh.md)

建议优先做三组机制实验：固定模型与预算比较反馈细节；比较仅生成和允许调用诊断工具；比较串行修订和多候选搜索。每组独立起跑，避免把此前修好的答案作为初始输入；用冻结的独立验收数据检查结果。重复次数与预算需在运行前确定，当前没有这些对照的结果。

## 7. 最终报告需要形成的设计结论

最终交付应使读者能够据此实现一个最小系统：写出任务合同，划分生成与验收的权限，定义迭代状态，接入数值和性能工具，制定保留与停止规则，保存每一步证据，再将候选接回模型。

其他开源项目的实验应逐一回答同样的问题：如何选优化目标、组织上下文、决定下一次动作、调用工具、保存记忆、判定成功及控制成本。只有核对过源码且跑过相应流程的部分，才写成已验证的框架差异。

本阶段已有证据支持明确职责边界和反馈需求；自动诊断的收益、搜索策略优劣、多框架机制差异和完整 block 价值仍需实测。后续实验的选择以能否验证这些设计问题为依据。

# AutoKernel 用法核对与 RMSNorm 性能上限：目前能说到哪一步

日期：2026-09-20。补充核对基于已冻结的上游提交 `78435821cc3d5756ba6ee1785c397f6d8fa8c90d`，不修改框架或已生成候选。本次新增的是源码审计与理论复算，没有新增 GPU 测量。

**现有结果证明候选在指定输入和计时方式下超过默认 compile；没有证明性能到顶，也没有完成 AutoKernel 官方模型示例的全流程复现。** 原报告缺少计算量、访存量、硬件计数器与停止依据之间的联系，必须补齐这些证据，才能回答“为什么不能继续加速”。

## 1. 上次使用了哪个流程

AutoKernel 有两个明确入口。[README](../../../README.md) 给出的模型流程是：

```text
prepare.py → profile.py → extract.py
    → program.md 指导 Agent 使用 bench.py 与 orchestrate.py 迭代
    → verify.py 回接模型验证
```

上次实际使用的是官方提供的另一条流程：

```text
kernelbench/bridge.py --source file
    → kernelbench/program_kb.md
    → kernelbench/bench_kb.py → 自主保留／回滚
```

因此，入口本身有上游支持，但它只验证了自定义算子的自主优化。它没有运行模型瓶颈提取、多算子调度和模型回接；也没有自动获得 `bench.py` 的 roofline 输出。两个入口不能互相代替。[启动器](../autonomous/run_trial.py)、[KernelBench 工作流](../../../kernelbench/program_kb.md)

原生说明期待每道题进行数十到数百次迭代；我们的试验硬预算为 900 秒，完成七次候选迭代。这是一次有限预算下的试验。框架在约 789 秒收尾，只能说明它遵守本次预算，不能解释为搜索收敛、达到硬件上限或没有其他优化办法。[运行记录](../evidence/autokernel-native-rmsnorm-r03/trial-summary.json)

## 2. 框架写了 roofline，是否就有可靠的瓶颈判断

Roofline（用计算吞吐与数据搬运吞吐约束性能的模型）需要正确的工作量、数据流量及硬件上限。源码审计发现，当前版本的这些环节仍需验证。

| 环节 | 当前源码行为 | 对 B300 实验的影响 |
|---|---|---|
| 模型瓶颈标签 | `profile.py:477` 的 `estimate_roofline_position` 主要按算子类型分类；未知类型再按时长猜测 | 标签是启发式判断，不是硬件计数器给出的实际瓶颈 |
| GPU 参数 | `bench.py:103` 与 `profile.py:101` 的已知 GPU 表没有 B300 | 会进入估算路径，不能把输出值直接当作 B300 官方峰值 |
| 未知 GPU 带宽估算 | 若有核心时钟字段，就用核心时钟和固定 256 位宽估计；否则采用默认值 | 缺少真实 HBM 总线与内存时钟依据 |
| 算力参照 | `bench.py:1073` 起使用 FP16 峰值求分界点和算力占比 | RMSNorm 的归约及普通算术不能直接用 Tensor Core 峰值衡量 |
| 停止规则的数据链路 | `orchestrate.py` 定义 `pct_peak` 阈值，但普通 `record` 入口只接吞吐、状态和描述，没有更新 `pct_peak` | 要实际核对该字段怎样进入调度状态，不能仅凭阈值定义就认定已按硬件上限停止 |

以上文件与冻结上游提交无差异。这些是当前版本的源码事实，不是已测得的 B300 故障。原生流程应先原样运行并保留输出，再由外部审计指出哪些字段可信；不能先替框架修好再称作原生结果。[bench.py](../../../bench.py)、[profile.py](../../../profile.py)、[orchestrate.py](../../../orchestrate.py)

## 3. 先算 RMSNorm 必须做多少工作

输入是 BF16（每个元素占 2 字节）的 `[1,S,D]`，这里 `D=1536`。每行需要平方、求和、求均值、加稳定项、求倒数平方根、归一化，再乘权重；中间 BF16 舍入保留原参考语义。[题目](../autonomous/wan_rmsnorm_problem.py)

先数一行两个元素的情况：平方 2 次，求和 1 次，乘均值系数 1 次，加稳定项 1 次，归一化乘法 2 次，权重乘法 2 次，共 9 次基础算术；另有 1 次倒数平方根与类型转换。一般化后，每行基础算术为 `4D+1`，所有行约为：

`F = S × (4D+1)`，另外记录 `S` 次倒数平方根及转换、线程间归约指令。

这个计数表示算法工作量。它不是精确的机器指令数，也不能把其中每种运算都按同一种 FP32 指令的成本相加。上游通用 RMSNorm 用 `6SD` 估算，是不同的计数约定；比较吞吐时需要统一约定。

在输入读取一次、输出写入一次、所有行共享的权重只从显存取一次、没有中间张量落到显存的理想条件下，逻辑数据量为：

`Q = 2SD + 2SD + 2D = 4SD + 2D` 字节。

大 S 时，`F/Q ≈ 1` 次基础算术每字节，属于低算术强度。它提示优先检查数据搬运、并行度及固定开销，但仍不能直接判定实际卡在 HBM（高带宽显存）。权重被每行读取、缓存重用、额外事务和寄存器溢出，都会使不同存储层的实际流量偏离这个理想数。

NVIDIA 给出的 B300 单卡 HBM 带宽最高为 8 TB/s。只有当上述 Q 真正经过 HBM 时，才可用 `Q / 8 TB/s` 求理想搬运时间。[NVIDIA HGX 参数](https://docs.nvidia.com/enterprise-reference-architectures/hgx-ai-factory/latest/components.html)

| S | 基础算术量 | 理想逻辑数据量 | 假设 Q 全经 HBM 的理想时间 | 已测候选时间 | Q/已测时间 |
|---|---:|---:|---:|---:|---:|
| 256 | 1.573 百万次 | 1.576 MB | 0.197 μs | 1.897 μs | 0.831 TB/s |
| 7,800 | 47.931 百万次 | 47.926 MB | 5.991 μs | 5.592 μs | 8.571 TB/s |
| 32,760 | 201.310 百万次 | 201.281 MB | 25.160 μs | 31.969 μs | 6.296 TB/s |

普通算力也要选对参照。NVIDIA 的 HGX B300 八卡规格给出 FP32 合计 600 TFLOPS，平均每卡 `600/8=75 TFLOPS`。将基础算术暂按该峰值粗略折算，三档计算时间约为 0.021、0.639、2.684 微秒，均低于表中的理想 HBM 搬运时间。这支持在冷数据的粗略模型下优先检查带宽；它没有包含倒数平方根、转换与归约等待，也没有证明本机在实际功耗和时钟下可达到这一峰值。[NVIDIA HGX 规格](https://www.nvidia.com/en-us/data-center/hgx/)

表内 MB、TB 使用十进制。耗时来自既有 Graph 计时，算术量与字节量是本次推算，逐项数据见[复算记录](../evidence/autokernel-native-rmsnorm-r03/roofline-estimate.json)。

中序列的 8.571 TB/s 超过标称 HBM 上限，说明不能把这种算法有效带宽当作真实 HBM 带宽利用率。原测量会反复使用同一组输入；缓存重用是需要验证的解释。还应核查实际事务量和测量口径，不能仅凭这个比值声称某一级缓存已经饱和。

长序列的 `6.296/8≈78.7%` 也只是将逻辑数据量放入理想模型得到的比值。它不能证明 HBM 实际利用率是 78.7%，更不能据此断言“最多还能加速约 1.27 倍”。短序列只有 64 个线程块，是候选的四行一块规则计算所得；它提示检查设备并行度，但未核对本机 SM 数和调度前，不能称为已证实的占用率瓶颈。

## 4. 真正回答“卡在哪里”需要哪些数据

`torch.profiler` 与 `nsys` 已确认短序列的调用和 kernel 发射。下一步需要 Nsight Compute（简称 NCU，采集单个 GPU kernel 的硬件计数器）区分显存、缓存、计算流水线和调度问题。它的重放及缓存控制会影响采集条件，必须明确记录，不能把默认采集等同于原来的热缓存 Graph 计时。[NVIDIA Profiling Guide](https://docs.nvidia.com/nsight-compute/ProfilingGuide/)

| 要回答的问题 | 应采集或校准的证据 | 可成立的判断 |
|---|---|---|
| HBM 是否接近饱和？ | DRAM 实际读写字节、吞吐、时钟；同卡持续读写带宽 | 实际 HBM 吞吐接近同条件可达上限，才支持显存带宽受限 |
| 是否主要由缓存服务？ | L1/L2 命中、事务量及吞吐；热输入与轮换输入对照 | 区分缓存收益和 HBM 搬运成本 |
| 计算流水线是否忙？ | 普通算术、特殊函数、转换指令的执行情况 | 使用实际执行的流水线参照，不套用 Tensor Core 峰值 |
| 寄存器是否限制并行？ | 每线程寄存器、理论与实际 occupancy、local memory 流量 | 区分寄存器限制和溢出造成的额外搬运 |
| GPU 是否没获得足够工作？ | grid/block、SM 数、活跃与可发射 warp、等待原因 | 区分短任务固定开销、并行度不足和依赖等待 |
| 是否确实搜索停滞？ | 独立配对复测、收益与预算曲线、停止日志 | 区分预算用尽、噪声、策略停滞和接近硬件上限 |

近似的性能下界应同时考虑 `Q_HBM/B_HBM`、`Q_L2/B_L2`、匹配流水线的计算时间，以及调度和依赖限制。这里的 Q 要用对应层级的实测流量。只取其中最大的理想项仍可能低估真实耗时，不能据此保证一定能优化到该数值。

外部诊断对冻结候选进行，不修改它，也不把诊断答案回送原试验。以后若给 Agent 增加硬件反馈，须另开配置标为“增强反馈”，与原生配置分开比较。

## 5. 官方示例应该怎样复现

先使用 README 自带的 `models/llama_7b.py` 中的紧凑 `LlamaModel`，输入 `[1,512]`、float16。文件名包含 7b，但该类是紧凑测试模型，不能把它写成实际 7B 复现。固定上游版本、原样模型、现有软件环境和第 4 张 GPU；不带入 Wan 候选或此前修复答案。

分三层验收：

1. **官方工具链能运行。** 在全新目录执行 README 的 `prepare.py`、`profile.py --model models/llama_7b.py --class-name LlamaModel --input-shape 1,512 --dtype float16`、`extract.py --top 5` 和 `bench.py`。逐步保留退出码、精度状态、profile、提取清单与硬件估算；执行成功不等于估算正确。
2. **官方 Agent 流程能完成。** 使用 `program.md`，记录分析计划、原生调度、自主修改、每轮评测、保留／回滚和停止依据。协调方只处理环境与预算，不替框架完成实现。原生 Phase A 包含计划确认，具体计划形成后按该阶段完成确认。
3. **候选确实回到模型并产生收益。** `verify.py` 通过之外，还要核对实际替换了哪些模块、优化 kernel 是否出现在 trace 中，再独立验证模型输出和端到端耗时。零替换后的“精度通过”不能算集成成功。默认 compile 的外部对照继续单列。

这是 B300 上的流程复现。README 的典型耗时和示意速度不是本机必须重现的数值目标。出现 B300 不支持、加载失败、提取错误或回接问题，先保留原生失败；任何兼容性补丁另记版本，不混成原生成功。

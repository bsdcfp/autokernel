## AutoKernel adaptation

Six explicit Wan tasks replace upstream extraction/prioritization for this
first campaign. `generate.py` passes the upstream program and frozen reference
to the configured coding model. It bounds one generation step, captures the
prompt, source, hashes, elapsed time and reported token usage, and stops for
source review before candidate execution. It does not initialize from optimized
answers. External fixed evaluation and KEEP/REVERT feedback complete each loop.

This is a **fixed-task Phase B adaptation**. Neither whole-model Phase A/C nor
the complete native orchestrator has been evaluated. A single generation step
is not a complete AutoKernel trial. Full-block integration, real activations,
frozen tolerances and repeat-trial budgets remain pending.

## Dtype boundary

The initial operator fixture uses BF16 activations, with FP32 modulation/gates.
That does not prove that every corresponding tensor in every real Wan block has
that dtype: residual paths and surrounding autocast can change it. The initial
T1 and RMSNorm generated kernels explicitly assume BF16 and must not be reported
as supporting the runner's optional FP32 mode. Freeze a captured real-block dtype
contract before making deployment or whole-block performance claims.

### Profiler findings and recovery

The valid torch traces contain five measured calls each. LayerNorm/modulation,
gated residual and RMSNorm each use one kernel per call in both implementations.
RoPE changes from four compile kernels per call to one candidate kernel; this
helps debug latency but did not improve medium/long latency. QK candidate uses
two kernels per call (separate q and k), not one joint QK kernel.

Initial nsys hardware-trace attempts produced either no report or a report with
no CUDA kernel table. The full-process diagnostic report contains
`ActivityFlushAll returned 35: CUPTI_ERROR_INSUFFICIENT_PRIVILEGES` and says
hardware tracing was used. These are failed captures, even when process exit is
zero or the report exists. The runner now selects `--trace=cuda-sw,nvtx,osrt`
and requires positive CUDA kernel instances from `nsys stats` before declaring
capture success. This uses the officially supported software trace without
changing host permissions: https://docs.nvidia.com/nsight-systems/UserGuide/#cuda-trace

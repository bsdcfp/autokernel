# AutoKernel 自主优化 Wan RMSNorm：一次不提供修复提示的试验

日期：2026-09-18。单次探索性试验，原生 KernelBench 自定义题目模式，B300 第 4 张卡。执行宿主为 Codex CLI，模型为 gpt-6-astra，推理级别 high。

**AutoKernel 在约 13 分钟内自行完成七次候选试验，最终实现通过三档独立精度检查。相对默认 torch.compile，中序列加速约 1.95 倍，长序列约 1.61 倍；短序列略慢。** 运行中协调方没有提供修复提示、修改候选或代替框架做保留/回滚决策。

本轮证明，在这道任务和当前预算下，框架能够自主调用工具、诊断失败、迭代实现并交付有用的候选。它尚不能证明其他算子、完整 Wan block 或其他模型配置也能取得相同结果。输入仍是合成数据。

## 1. 这次怎样保证测的是自主过程

笔者先冻结了[评测协议](autonomous-evaluation-protocol.zh.md)，再启动独立进程。任务只有原始 Wan RMSNorm 计算，未提供此前生成的优化代码或数值修复答案。

AutoKernel 上游版本固定为 `78435821cc3d5756ba6ee1785c397f6d8fa8c90d`。通过原生 `bridge.py --source file` 装入题目，使用原样的 `kernelbench/program_kb.md` 和 `bench_kb.py`。这道题是我们提供的 Wan 任务，不是 KernelBench 官方数据集题目。

框架获得 shell、编译器、GPU 和诊断工具，自己决定如何修改、测试、保留或回滚。协调方只负责启动、只读观察、资源边界、预算和结束后的验收。本轮没有运行 AutoKernel 全模型分析与整体验证阶段，也没有验证其多算子编排器。

| 约定 | 本轮执行情况 |
|---|---|
| 从干净状态起跑 | 上游快照导出为新 git 仓库，由原生 bridge 生成参考逻辑 starter |
| 保留原生优化循环 | 框架自己读工作流、生成代码、调用测试、记录结果和回滚 |
| 限制可修改范围 | 运行后受保护的框架文件、题目和参考文件哈希全部一致 |
| 不提供运行中帮助 | 干预记录为空；框架自行处理实现和诊断脚本中的问题 |
| 有限预算 | 硬上限 900 秒，要求在 810 秒左右收尾；实际自行退出于 788.851 秒 |
| 结果独立验收 | 退出后冻结候选，新进程、新随机输入，另测默认 compile 与候选 |

运行边界是 AIS 容器，GPU 通过 UUID 固定。当前没有正式防作弊隔离：不能读取旧实验的规则依赖任务合同，不能把干净目录等同于强隔离。运行元数据见[本地记录](../evidence/autokernel-native-rmsnorm-r03/trial-summary.json)。

## 2. 框架实际做了哪些决策

框架从 Triton（GPU kernel 编程工具）的单行归约开始，随后测试多行组织、CUDA 向量化读取和累加链。CTA（CUDA 线程块）在这里是一组一起处理若干输入行的线程。

下表保留了每次候选试验。耗时来自框架原生普通调用计时，单位微秒；它使用 eager（原生逐步执行）作参照，不能混入后面的独立 Graph 计时。

| 候选轮次 | 修改假设 | 原生候选耗时 | 框架决策 |
|---|---|---:|---|
| 1 | Triton 每块处理一行，保留 BF16 中间舍入 | 45.0 | 保留 |
| 2 | Triton 每块处理四行 | 24.7 | 保留 |
| 3 | CUDA 向量化读取，每块处理四行 | 24.7 | 保留，理由是相对 eager 比值提高 |
| 4 | 增加每块行数，对短序列另选配置 | 25.6 | 回滚 |
| 5 | 使用四条独立 FP32 累加链 | 24.5 | 保留 |
| 6 | 使用流式写回，尝试减少缓存污染 | 25.3 | 回滚 |
| 7 | 保留对齐输入的向量化路径，增加非对齐视图回退 | 16.2 | 保留，之后复测仍为 16.2 |

以上七次是同一次自主运行里的候选迭代，不能当作七次独立 Agent 实验。数据摘要来自[原生决策表](../evidence/autokernel-native-rmsnorm-r03/native-decisions.json)。

**它确实自行处理了失败。** 配置扫描尝试每块处理 32 行时，GPU 报寄存器资源不足，框架记录失败并继续较小配置。它还在自己的默认 compile 诊断中遇到 Python 模块同名遮蔽，自行修改诊断脚本的导入顺序；没有修改框架评测代码。

这些行为表明，工具错误通常可以成为缩小搜索范围的依据。但这仍然是运行后排除失败配置，本轮没有证明框架能在生成前通过硬件模型剪掉全部非法组合。

**候选 3 暴露出选择规则的弱点。** 候选 2、3 的原生耗时都显示为 24.7 微秒，eager 基线却从 127.7 变成 133.9 微秒。框架据此记录更高的相对加速并保留 CUDA 版。基线波动也能提高这个比值，因此不能把这一步视为已经证实的性能改善；通常还需要配对复测和波动判断。

候选 7 的耗时明显下降，但这一步的收益仍需进一步归因，不能仅凭轮次名称，把全部收益归因于增加非对齐回退。最终性能以独立计时为准。

## 3. 最终生成的算子是什么

最终候选是 CUDA C++ 实现。它按向量读取 BF16（16 位浮点格式）数据，使用四条 FP32 累加链计算归约，每个线程块处理四行，再完成归一化和权重乘法。中间归一化结果先舍入到 BF16，沿用参考的计算语义。

例如，把某行所需的数据分给多个线程之后，每个线程先累加自己负责的部分，随后合并成整行统计量；独立累加链减少同一条累加依赖上的串行等待。这里描述的是源码采取的结构，是否因此更快仍要看实测，不能单凭结构判断性能。

向量化路径要求地址对齐。对于起始地址不满足对齐要求、但本身连续的视图，候选回退到原生 ATen 计算。因此，报告中的加速范围是本轮测量的常规对齐输入，不能外推为所有连续视图都获得同样收益。

完整[候选源码](../evidence/autokernel-native-rmsnorm-r03/kernel.py)已经取回本地，其 SHA256 与远端冻结版本相同：`c5efdcaa00fc7483766598bfa9c7a45f24dc9bc8809530091006ec9236055944`。源码审阅确认使用当前 CUDA stream，未发现读取测试答案、按随机种子分支或缓存输出的逻辑。

## 4. 独立验收：超过默认 compile 多少

S 表示一次处理的 token 数，即输入 `[1,S,1536]` 的行数。本轮用 256、7,800、32,760 三档；每行有 1,536 个特征。

验收使用新的基础随机种子 607，包含其他随机输入、重复输入、首输入整体加 2，以及 CUDA Graph 换输入重放。CUDA Graph（记录后重放一组 GPU 操作）计时捕获 32 次调用，重放 50 次，再报告每次调用的中位耗时。编译与 profiler 不计入这组速度分数。

候选和默认 compile 三档均通过冻结的 `.01 + .01 × abs(reference)` 逐元素门限，且检查了输入不变性、形状、类型、设备和有限值。该门限仍是合成算子实验设置，不是视频质量认证。

| 输入规模 | 默认 compile | 自主生成候选 | 加速比 | 结论 |
|---|---:|---:|---:|---|
| S=256 | 1.839 μs | 1.897 μs | 0.97 倍 | 候选略慢 |
| S=7,800 | 10.879 μs | 5.592 μs | 1.95 倍 | 候选更快 |
| S=32,760 | 51.406 μs | 31.969 μs | 1.61 倍 | 候选更快 |

以中序列为例，`10.879 ÷ 5.592 ≈ 1.95`。短序列对应 `1.839 ÷ 1.897 ≈ 0.97`，小于 1 说明候选较慢。精确值和计算结果见[独立计时记录](../evidence/autokernel-native-rmsnorm-r03/independent-timing-summary.json)。

框架最终报告的 7.99 倍是相对 eager 的内部普通调用成绩；它自己另外测出的约 1.99 倍是默认 compile 的 Graph 对照。我们的独立新输入得到约 1.95 倍，通常应以独立结果作为本次对外结论。这些都是一次试验的数据，没有独立重复运行的置信区间。

## 5. 两种 profiler 核对实际执行

独立 `torch.profiler` 在短序列的五次调用中，默认 compile 与候选都发射五个 kernel，即 `5 ÷ 5 = 1` 个 kernel 每次。默认基线是 Inductor 生成的 Triton 归约，候选是 `rmsnorm_kernel`。短序列采集没有显示发射次数减少；中长序列的收益还需要对应规模的采集和更细的硬件指标来归因。

五次调用的累计 GPU kernel 时间分别为 10.817 和 10.081 微秒；它们属于 profiler 条件，不能替换上一节的独立 Graph 计时，也不能据此改写短序列的速度结论。

独立 `nsys` 补采也成功，两个实现均在 `wanbench/wan-rmsnorm` 标记范围内记录五个 kernel。默认 compile 的累计 GPU kernel 时间为 10.752 微秒，候选为 10.080 微秒。统计只包含标记范围，排除了初始化、预热和精度检查产生的其他 kernel；采集摘要见[两种 profiler 记录](../evidence/autokernel-native-rmsnorm-r03/profiler-summary.json)。

两种工具都核实了短序列实际执行的实现与发射次数。这里只完成短序列 profiler 采集，没有测量中长序列的内存带宽或寄存器占用，因此不把向量化、累加链等源码结构直接写成已证实的加速原因。

## 6. 这次能归纳出哪些 Agent 设计模式

| 设计问题 | 本次观察 | 可以支持的结论 |
|---|---|---|
| 谁决定下一步？ | 框架自主选择 Triton、CUDA、配置扫描和累加结构 | 模型可以在工具反馈下组织实现探索 |
| 错误怎样进入下一轮？ | 记录寄存器不足，修复诊断脚本导入问题 | 有执行工具和错误记录的循环具备实际恢复能力 |
| 怎样保存搜索状态？ | git 候选历史、results.tsv、每轮日志与最终复测 | 文件与版本记录可以承载迭代记忆 |
| 怎样判断改善？ | 有回滚，但也保留过候选耗时持平、基线变慢的结果 | 通常应把有效性检查与统计可靠的选择规则放进控制器 |
| 谁确认最后成功？ | 框架内部通过后，由外部程序用新输入复核 | 生成、内部搜索评测和最终验收可以分别承担职责 |
| 何时停止？ | 在硬预算前自行收尾并提交最终候选 | 本次遵守预算；不能据此证明停止点最优 |

本次没有统一模型对照、反馈消融或多个框架的独立重复实验。因此，以上是有执行记录支持的能力观察，尚不是各设计模式的因果收益排名。对于框架优劣，通常还要比较相同任务和预算下的成功概率与成本分布。

## 7. 成本、失败与数据边界

自主阶段用时 788.851 秒，约 13 分 9 秒；包含框架自己的工具执行，不包含协调方环境准备和结束后的独立验收。完成 56 次命令调用。CLI 汇总输入 token 为 2,019,653，其中缓存输入 1,917,312；输出 19,778，其中推理输出 9,535 已包含在输出总数中。这不是 56 次独立试验，也不直接换算成账单。[运行记录](../evidence/autokernel-native-rmsnorm-r03/trial-summary.json)

首个正确候选的精确累计成本本轮未单独计量。工具过程保存在远端事件日志，不用最终总成本冒充首次成功成本。

失败记录均保留：

- **r01**：附加写入沙箱导致 CUDA 304，框架自行诊断并停止。
- **r02**：未显式配置执行权限，CLI 使用只读默认环境，框架自行停止。
- **r03**：框架运行成功；内部保留资源不足、诊断导入失败和性能回退记录。
- **外部验收第一版**：我方依赖路径把上游 profile.py 暴露给标准库，compile 加载失败；修正加载路径后在新目录完成配对验收。
- **nsys 首次采集**：默认临时目录无写权限；改用独立可写临时目录后单独补采，不重复已经通过的计时。

候选源码及本报告引用的摘要已取回本地。完整事件日志、所有候选历史、原始测量 JSON 和 profiler trace 仍在实验机：`autonomous_trials/autokernel-native-rmsnorm-r03/`。摘要不能代替这些原始文件，完整实验包尚未回传。

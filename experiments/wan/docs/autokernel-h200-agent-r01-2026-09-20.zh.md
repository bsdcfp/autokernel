# AutoKernel 在 H200 上的自主实验：会调优，但尚未证明能判断性能极限

2026-09-20 · 官方紧凑 Llama 示例 · 一次自主试验

**AutoKernel 能驱动 Agent（智能体）自行修正精度、尝试优化和回滚；这轮没有交付模型加速，也没有完成硬件瓶颈诊断。** 框架、模型和评测器均保持原样，协调方没有在运行中提供算法或修复代码。

## 这次做到了什么

Agent 在 **19 分 23 秒**内完成 **36 次候选评测**，保留 4 个候选，原生精度检查均通过。5 项计划中，第 5 项未开始，第 4 项仍有搜索余量；不能写成五项全部完成。首次通过原生精度检查大概用了 4 分钟。[运行记录](../evidence/official-h200-agent-r01/raw/trial.json)、[完整实验表](../evidence/official-h200-agent-r01/raw/workspace/results.tsv)

模型回接的原生记录是 **4.58 → 7.39 ms，速度比 0.62×**。例如，原来约 4.6 毫秒完成的工作，换上候选后约需 7.4 毫秒。矩阵乘法接入了模型，attention 没有对应接入逻辑，被跳过；汇总却仍把 4 个加载的候选都列成了“已替换”。[回接日志](../evidence/official-h200-agent-r01/raw/workspace/workspace/pilot/verify.log)

Agent 自己发现并说明了这些限制，没有把单算子收益冒充模型收益。矩阵乘法包装器每次调用都会复制转置后的权重，它可能贡献了额外开销；目前只有源码依据，尚未单独测量这一开销的占比。

## 独立验收：attention 更快，matmul 的 GPU 执行更慢

4 个候选通过全部 **296 项新输入检查**，包括多形状、多精度和输入不变性。matmul 对 FP32 及非 32 对齐尺寸使用 PyTorch 回退，因此不是全部输入都运行新 kernel。下面用两个代表候选展示削弱 CPU 发射间隙后的结果；速度比大于 1 才表示更快。

| 默认主测量 | 默认 compile | 候选 | 速度比 |
|---|---:|---:|---:|
| 矩阵乘法，三个维度均为 2048 | 26.64 μs | 32.26 μs | 0.82× |
| 因果 attention，批次为 2、32 个头、序列 1024、头维度 64 | 166.43 μs | 51.20 μs | 3.25× |

这是外部新增的 CUDA Graph 配对复测，与原定普通调用计时分开。普通调用受 CPU 发射影响：矩阵乘法曾显示加速，torch.profiler、nsys 和 Graph 复测却一致显示其 GPU 计算更慢。attention 在两种计时方式下都有收益；它仍未接入模型。

验收使用另一台空闲 H200 的第四张卡，双方在同一设备、同一环境下比较。完整条件、原定计时、模型实际矩阵形状、理论工作量及 NCU 数据见[独立验收与瓶颈分析](autokernel-h200-external-analysis-2026-09-20.zh.md)。这些事后数据不计为 Agent 自主完成。

## 按我们的五项标准看

| 能力 | 本轮证据与判断 |
|---|---|
| 算清上限 | 识别出 H200 峰值利用率超过 100% 的异常，但没有重建正确的算力、带宽上限 |
| 找到瓶颈 | 做了模型热点分析；没有调用 NCU（GPU 硬件计数器分析器）或取得等效硬件计数器，未验证实际计算或访存瓶颈 |
| 有据修改 | 数值问题有诊断实验；性能修改有事前假设和计时，但寄存器、缓存、流水线解释没有前后硬件数据支持 |
| 验证结果 | 自行完成原生精度和模型回接，承认模型变慢；默认 torch.compile 由外部另行验收 |
| 合理停止 | 明确按预算收尾，保留未完成任务；没有声称已到硬件极限 |

例如，Agent 将矩阵乘法的分块从 `64×64×32` 改为 `128×128×64`，原生主测量从约 50 μs 降到 33 μs。这个结果证明修改改善了该测量，不能证明“寄存器压力是原来的瓶颈”：它没有测寄存器数量、占用率及其变化。扩大另一种分块后反而慢到约 203 μs，Agent 随即回滚。[假设和决策记录](../evidence/official-h200-agent-r01/raw/workspace/workspace/pilot/notes.md)

## 对 Agent 架构的启示

AutoKernel 的基本结构是：`program.md` 规定工作方式，语言模型提出并实现假设，`bench.py` 返回精度和耗时，`orchestrate.py` 保留结果并选择下一项，最后由 `verify.py` 回接模型。本轮证明这条循环可以自主运行。

从这次结果看，我们设计 Agent 时还需要三个明确职责：

- **核验硬件反馈。** 超过物理上限的指标应被标为无效；诊断模块给出与当前精度、存储层匹配的数据，优化决策才能引用它。
- **核验模型接入。** 记录实际替换的模块及执行的 kernel。候选文件被加载，不代表模型使用了它；单算子更快也不保证接入后的整条路径更快。
- **让停止理由可检查。** 保存收益、失败假设、预算与未知项。连续回滚说明当前搜索停滞，不能证明硬件已经没有余量。

这三点是本轮证据支持的设计建议，尚未通过增强版 Agent 对照实验验证。它们已补入[Agent 架构与设计模式阶段稿](operator-agent-design.zh.md)。

## 条件与边界

使用官方 **124.7M 参数**的紧凑 `LlamaModel`，输入 `[1,512]`、FP16；不是实际 7B，也不是 Wan。提取的 5 项均退回默认形状，因此搜索覆盖的是框架默认题目，不能当成模型真实形状的优化结果。

自主试验运行在 `x2v-hold-h200-master-0` 的第四张 H200，CLI 0.155.1、`gpt-6-astra / medium`，上游固定为 `7843582`。52 个受保护文件的哈希没有变化。它还读取了宿主的调试、验证等 5 项技能，因而应标为**原生工作流加宿主技能**，不能将全部表现归因于 AutoKernel 自身。

CLI 报告输入约 816 万 token，其中 98.5% 来自缓存；输出约 2.38 万 token。142 次 shell 命令不等于 142 次模型请求。未取得实际账单；这是一次试验，不能推断成功率。[审计记录](../evidence/official-h200-agent-r01/audit.json)

原始候选、失败版本、命令事件和日志已完整保存为[可恢复归档](../evidence/official-h200-agent-r01/agent-trial.tar.gz)，附 [SHA256](../evidence/official-h200-agent-r01/agent-trial.sha256)。独立验收的原始结果另存于[验收归档](../evidence/official-h200-agent-r01/acceptance.tar.gz)。

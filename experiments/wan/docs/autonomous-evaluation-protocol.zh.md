协议版本：v2，更新于 2026-09-20。用户确认：评测完整 Agent 过程；协调方 Codex 不干预框架实现过程；Agent 应自主取得性能证据，并据此提出修改、验证与停止。

版本边界：2026-09-18 的 r01/r02/r03 仍按当时冻结配置解释。以下新增标准用于后续预注册试验；对旧试验只能根据已有轨迹追加回顾审计，不能补采数据后冒充当时 Agent 已完成的诊断。文档更新不代表启动器已自动执行这些检查。

## 目标与单位

通过真实实验解释 Agent 的原理、架构和设计模式。一次试验是从干净候选开始，在预算内自主读取任务、提出假设、调用工具、测试、诊断、修订、保留或回滚并交付结果的完整过程。模型调用次数不是独立试验次数。

## 权责边界

- 固定：任务语义、允许修改范围、输入分布、独立验收门限、硬件、工具、预算和记录方式。
- 框架自主：假设、优化算法、工具选择、诊断方式、迭代路径、候选保留和停止。
- 协调方仅负责启动、资源和超时管理、只读观察、运行后的源码审阅与独立验收。不发送运行中反馈，不修改候选，不提供历史修复答案，不接管决策。
- 框架自行调用评测得到的错误属于正常反馈；人工补充定位或算法属于辅助条件，不能混入本次自主成绩。
- 若框架、工具或环境失败，如实记录。开始后的修复不得悄悄覆盖原试验；环境修复后重跑必须用新试验编号。

## 评分与证据

记录任务理解、搜索规划、工具使用、错误恢复、保留/回滚决策、预算管理、最终交付。以动作与工具结果证明能力，不按推理文字长短评分。

最终结果同时报告：编译/执行成功，独立多形状正确性，默认 compile 的有效配对加速，首个正确候选成本，首个有效加速成本，最终性能，所有失败及人工介入。未测指标填写未测，不能用模型调用次数代替 trial 数。完整 block 收益另行验收。

框架原生配置与统一模型控制变量实验分别报告。各框架保留自身搜索机制；适配只负责接口、环境与测量接入。独立试验使用干净上下文与目录，不访问先前候选、人工诊断、其他试验结果。正式重复次数和总预算应预注册，本次单次 pilot 不做成功率或排名推断。

## 性能诊断与决策能力：必须审计的证据链

**相对基线更快是效果证据，不足以证明 Agent 理解瓶颈、搜索高效或接近性能上限。诊断数据必须由被测 Agent 在运行中自主取得、解释并用于决策。** 协调方在结束后采集的数据只用于外部验收，不计入 Agent 自主诊断成绩。

| 环节 | Agent 应完成的动作 | 审计所需证据 |
|---|---|---|
| 建立性能预期 | 推导计算量、访存量、算术强度和适用的性能上限 | 公式、shape/dtype、运算计数约定、硬件来源；区分普通算术与 Tensor Core、稀疏与稠密峰值；说明缓存假设 |
| 判断实际瓶颈 | 主动调用 NCU 或能回答同一问题的等效工具 | 工具命令、版本、退出状态、原始指标；按假设检查 DRAM/L2、计算流水线、寄存器、占用率或调度等待 |
| 提出针对性修改 | 将修改与瓶颈联系起来，给出可被否定的预测 | 修改前的假设记录、预计改变的指标、候选代码版本；不能只有“试试某个参数” |
| 验证修改 | 检查精度、配对性能及目标指标变化 | 修改前后同条件指标和耗时、误差结果、测量波动；证据不支持时撤回或修订解释 |
| 继续、回滚或停止 | 根据实测收益、剩余空间与预算做决定 | 决策、引用的运行记录、失败假设和停止原因；预算到时不等于达到硬件极限 |

例如，Agent 假设寄存器压力限制并行度，就应先取得寄存器与占用率证据，再针对该问题修改，并复查这些指标和精度、耗时。耗时下降但预期指标未变，不能算该瓶颈解释得到验证；应记录为效果改善、机制尚未验证。观察到指标共同变化也不自动构成严格因果证明，必要时做受控对照。

### 采集覆盖与口径

- 预注册任务声明的每档形状均要有最终候选的诊断证据。当前 Wan 三档为 S=256、7,800、32,760；不得用短序列推断中长序列瓶颈。若合并形状，必须在运行前说明依据并限定结论范围。
- 不要求每次迭代完整运行 NCU。至少审计初始瓶颈判断、关键优化假设和最终交付／停止判断所依据的证据；性能改善的归因须有对应修改前后的对照。
- 工具可替代，证据不能省略。普通计时或 kernel 次数不能替代 DRAM 流量、缓存吞吐、寄存器或调度指标；框架按算子类型输出的标签也不算硬件实证。
- 逻辑输入输出字节量除以耗时，记为算法有效带宽。真实 HBM 利用率须使用实测 DRAM 流量及匹配的带宽参照，不能直接拿热缓存 Graph 计时除以冷数据理想时间。
- 记录缓存控制、预热、重放方式、GPU 时钟／功耗状态、并发占用及采集覆盖。诊断与速度评分分开；不得将 profiler 内的耗时混入独立性能排名。
- 工具发现、诊断和复测全部计入 Agent 的时间与调用成本。运行前可以检查工具安装和权限，不能替 Agent 预先诊断题目并传入答案。

### 逐环节评分与缺失处理

对上表五个环节逐项记录下列等级，不以平均分掩盖证据缺口；正式汇总权重需另行预注册。

| 等级 | 判定 |
|---|---|
| 0：未执行 | 完整轨迹显示没有执行相应动作 |
| 1：无有效支撑 | 有陈述或尝试，但数据缺失、口径错误，或不足以支持结论 |
| 2：有有效证据 | 已取得或推导可核对证据，但没有形成相应的后续决策／验证闭环 |
| 3：形成闭环 | 证据来源与条件有效，并实际用于对应环节的决策或验证，结论范围与证据一致 |

另列状态：`工具受阻`、`记录缺失`、`外部辅助`。工具因权限等原因失败，保留尝试和错误，可评价恢复行为，但不授予未取得的瓶颈证据分；轨迹不完整时记 `未验证`，不能直接断言未执行。外部帮助单列，不折算成自主得分。不得删除这些 trial 或将缺失值默认为通过。

最终分别报告：**产物效果、性能诊断、决策质量、自主程度、成本与停止依据**。只有加速通过的试验可称为产生有效加速；只有相关诊断和决策证据闭合，才能声称已验证其自主性能分析能力。即使诊断充分，也须允许“剩余空间未知”的结论，不要求 Agent 为取得高分编造已到极限。

### 轨迹与证据归属

每条关键假设／决策至少保存：trial 与配置版本、时间、假设编号、候选提交或哈希、输入形状与 dtype、工具命令及原始结果路径、指标单位与采集条件、预测、观察、保留／回滚决定及理由、累计预算、尚未排除的解释。

同时标记证据产生方：`Agent 运行中自产`、`协调方运行后采集` 或 `运行中外部辅助`。假设记录必须先于针对该假设的结果；不能把最终总结中的事后解释当成预先预测。引用相应源码、日志、trace/report 与哈希，最终文字自述不能代替工具轨迹。

停止原因至少区分：`预算耗尽`、`环境／工具阻塞`、`搜索策略停滞`、`有证据接近指定硬件上限`、`主动停止但依据不足`。若声称接近上限，须同时给出匹配存储层／计算流水线的上限来源、实测指标、噪声与未建模开销；不能仅凭连续失败或较高的有效带宽判定。

## 原生配置、增强配置与官方示例复现

- **原生配置**：保留官方工作流和搜索机制。评测人员用本协议审计它是否自行取得并使用证据，不向原生提示额外加入诊断步骤或补足缺失的硬件分析。未执行就如实记录；不替框架补做后宣称原生成功。
- **增强配置**：若增加明确的诊断要求、工具接口、硬件反馈、提示、技能或控制器逻辑，另开 trial，冻结并保存相对原生配置的差异。再比较能力与成本，不能合并为原生框架成绩。统一模型的控制变量实验也要明确属于哪种配置。
- **先验证官方用法**：先复现固定版本的官方示例，再迁移 Wan。分别验收官方工具链、原生 Agent 循环、真实模型回接及端到端结果；只有部分入口可运行时，只报告其已验证范围。官方自带 starter 可用，不能导入已有优化答案。
- **AutoKernel 对应入口**：官方紧凑 `LlamaModel` 示例走 `prepare.py → profile.py → extract.py → program.md/bench.py/orchestrate.py → verify.py`。核对实际替换和 kernel 执行，不能把零替换的精度通过当成集成成功。KernelBench custom-file 的成功不代替这条流程复现。
- 原生示例失败与任何兼容性修订分开保存。协调方不修改被测框架来填补能力缺口；确需修订时另立配置并明确来源。具体核对见[用法与性能上限补充报告](bottleneck-and-native-example-audit-2026-09-20.zh.md)。

## 历史冻结配置：autokernel-native-rmsnorm-r01（2026-09-18）

- 完整性：运行前后比较框架、题目及内部评测文件哈希。记录所有生成事件与命令；被 git 回滚的候选通过事件日志与最终 git 对象备份保留可追踪线索。
- 隔离限制：workspace-write 是宿主写入边界，当前不是正式防作弊沙箱；只读访问既往结果由任务合同禁止，日志审计访问行为。独立验收材料不放入候选目录；不能宣称强隐藏测试。
- 备份：自有题目、协议和启动器必须先推送 GitHub 再部署；候选及结果运行后另行备份。

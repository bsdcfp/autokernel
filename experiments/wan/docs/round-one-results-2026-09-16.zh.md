# AutoKernel 优化 Wan 算子：哪些已通过，哪些真正变快了

报告更新：2026 年 9 月 18 日。实验数据截至 9 月 17 日，覆盖一张 B300 上的六个算子、三种输入长度。

**六个算子候选都已通过当前合成输入的精度检查。** LayerNorm 加调制、RMSNorm 相比默认 `torch.compile` 有可复测的性能收益；QK Norm 加 RoPE 的融合精度问题也已修复。默认 compile 的 QK、Linear 加 GELU 两项基线仍未通过检查，因此这两项暂不报告相对 compile 的加速比。

这里的候选，指 Agent 生成并经过修订的算子实现。笔者与评测程序提供了源码诊断、反馈和独立验证；实验尚未覆盖真实视频输入及完整 Wan block 的端到端耗时。

## 1. S 是什么：一次处理多少个视频 token

**S 是序列长度，表示一次送入算子的 token 数。** Token（模型处理的一个数据单元）在这里对应视频特征网格中的一个位置。它通常已经经过模型前面的编码与切分，不能直接把一个 token 当作一帧原始视频或一个像素。

可以把输入想成一张表：有多少个 token，就有多少行；本轮每行固定有 1,536 个特征数值。S 变大，就是这张表的行数变多。

本轮用时间、高度、宽度三个方向的网格生成合成输入。例如，一个有 2 个时间位置、每个位置排成 3 行 4 列的网格，包含 `2 × 3 × 4 = 24` 个 token，即 `S=24`。实际使用的三档输入如下，定义见[输入生成代码](../wanbench/tasks.py)。

| 本文称呼 | 特征网格：时间 × 高度 × 宽度 | 序列长度 S |
|---|---|---:|
| 短序列 | 1 × 16 × 16 | 256 个 token |
| 中序列 | 5 × 30 × 52 | 7,800 个 token |
| 长序列 | 21 × 30 × 52 | 32,760 个 token |

原表最后一列的完整数字是 **32,760**，不是 32。这三档通常用来检查输入变大后，精度和速度是否仍然成立。它们是特征网格大小，本报告不据此换算原始视频的时长和分辨率。

## 2. 还有失败吗：候选已通过，两项默认基线仍未通过

实验中有三种实现，各自承担不同作用：

- **eager（原生逐步执行）**：按冻结的 PyTorch 参考代码计算，提供精度检查的参照输出。
- **默认 compile（性能基线）**：对同一参考代码调用 `torch.compile`，使用默认编译模式。它也要先通过精度检查，才能参与速度比较。
- **Agent 候选（被评测实现）**：由 AutoKernel 提示策略和固定任务适配器生成代码，再经过外部测试及反馈修订。

当前状态见下表。每个通过都只覆盖本轮测试过的输入、形状和误差门限，不代表已验证任意视频或模型输出质量。

| 算子与作用 | 当前候选精度 | 默认 compile 精度 | 目前能得出的结果 |
|---|---|---|---|
| LayerNorm 加调制：归一化后按条件缩放、平移 | 三档通过 | 三档通过 | 中、长序列有性能收益 |
| Gated Residual：按门控系数加入残差 | 三档通过 | 三档通过 | 基本持平，候选略慢 |
| RMSNorm：按均方根归一化 | 三档通过 | 三档通过 | 中、长序列有性能收益 |
| RoPE：用旋转加入位置信息 | 三档通过 | 三档通过 | 短序列更快，中、长序列未超过基线 |
| QK Norm 加 RoPE：归一化注意力的查询、键，再加入位置 | 最新融合版三档通过 | 三档未通过 | 已修复候选，保留两个融合 kernel |
| Linear 加 GELU：线性变换后接激活函数 | 修订版三档通过 | 三档未通过 | 本轮精度通过，暂不能与默认 compile 计算有效加速比 |

**精度未通过，表示数值差异超过了本轮设定的容许范围，不等于程序崩溃。** 本轮通常使用逐元素规则 `绝对误差 <= 0.01 + 0.01 × 参考值的绝对值`。例如参考值为 1，容许误差就是 `0.01 + 0.01 × 1 = 0.02`；输出 1.01 通过，输出 1.03 不通过。回到上述六项算子，每个输出数值都要接受这类检查，同时检查形状、数据类型和输入是否被改写。

这个门限是探索性检查的设置，尚未用真实模型质量验证来确定。通过之后，通常还需要接回模型验证最终结果；未通过时，本轮不会把该实现的耗时用于计算加速比。

### QK 候选已经怎样修好

旧报告里的 QK 候选只通过短序列，中、长序列有失败。排查发现，累加顺序的微小差异会让归一化结果落到相邻的 BF16（16 位浮点格式）数值，经过后续运算，最终输出可能越过误差门限。

先前的兼容方案保留原生 Norm，精度通过，但每次调用需要 18 个 kernel（GPU 上发射执行的计算函数）。最新融合版复现了原生归约的累加次序，并保留中间舍入步骤，回到 **每次两个 kernel**。

最新版本在三种长度、两批随机种子下，完成 24 次普通检查（含重复检查）和 6 次图重放检查，全部通过；最大绝对误差约 `7.28e-12`。我们没有放宽门限。具体数值反例与检查记录见[QK 融合修复报告](fused-precision-repair-2026-09-17.zh.md)。

### 为什么默认 compile 还没全部通过

默认编译器可能改变中间精度转换和运算顺序。本轮 QK 基线受到中间舍入与归约差异的影响；Linear 加 GELU 基线则把加 bias 的线性计算拆开，改变了 BF16 舍入的位置。

Linear 加 GELU 在关闭部分图优化，或保留 Linear 中间输出后，三种长度的诊断均与 eager 逐元素一致。但这些设置已经改变了默认基线，不能直接沿用其名称或旧的性能比较。源码与对照记录见[编译器精度排查](precision-investigation-2026-09-16.zh.md)和[三档补跑结果](precision-followup-2026-09-17.zh.md)。

因此，旧表中的 `精度失败 / 207.698` 实际表示：**默认 compile 未通过精度检查；候选通过，耗时 207.698 微秒。** 本文将精度状态和耗时分开列出。

## 3. 性能：把基线与候选分别列出来

所有耗时单位均为 **微秒（μs）**，数值越小越快；`1,000 μs = 1 ms`。下表每一行只对应一种实现，不再把两种实现挤进同一个单元格。

### 四项可以与默认 compile 比较的算子

下表采用原先已通过精度检查的配对测量数据。两类 Norm 使用复测结果，Gated Residual 和 RoPE 使用首轮结果。当前配置保留 RoPE 初版；其后一次性能修订没有带来跨长度的一致改善，记录保留在[历史附件](archive-round-one-results-2026-09-16.zh.md)。

| 算子 | 实现 | 短序列：256 token | 中序列：7,800 token | 长序列：32,760 token |
|---|---|---:|---:|---:|
| LayerNorm 加调制 | 默认 compile | 2.543 | 28.857 | 115.835 |
| LayerNorm 加调制 | Agent 候选 | 2.242 | 20.102 | 80.931 |
| Gated Residual | 默认 compile | 1.664 | 15.151 | 60.374 |
| Gated Residual | Agent 候选 | 1.790 | 15.278 | 60.922 |
| RMSNorm | 默认 compile | 1.813 | 10.840 | 51.507 |
| RMSNorm | Agent 候选 | 1.645 | 8.195 | 41.274 |
| RoPE 初版 | 默认 compile | 9.160 | 96.092 | 374.531 |
| RoPE 初版 | Agent 候选 | 4.732 | 97.165 | 402.498 |

以中序列 LayerNorm 加调制为例，基线耗时 28.857 微秒，候选耗时 20.102 微秒，加速比为 `28.857 ÷ 20.102 ≈ 1.44`。同样的方法算出，LayerNorm 加调制在中、长序列约为 **1.43–1.44 倍**，RMSNorm 约为 **1.25–1.32 倍**。这些是本轮实测结果，通常不能直接换算成整段视频生成的加速比。

RoPE 的对比也说明，短序列快不代表长序列快：它在短序列从 9.160 微秒降到 4.732 微秒，长序列却从 374.531 微秒升到 402.498 微秒。

### QK 与 Linear 加 GELU：候选耗时已测，默认基线暂不可比较

下表两行都已通过当前精度检查。默认 compile 未通过的状态已在前面的精度表中说明，不填入耗时单元格。

| 算子 | 当前候选版本 | 短序列：256 token | 中序列：7,800 token | 长序列：32,760 token |
|---|---|---:|---:|---:|
| QK Norm 加 RoPE | 完整融合版 r03 | 12.760 | 241.656 | 984.280 |
| Linear 加 GELU | 修订版 r02 | 10.190 | 207.698 | 855.654 |

QK 的新数据来自[融合修复后的测量](fused-precision-repair-2026-09-17.zh.md)，Linear 加 GELU 数据来自[首轮测量](archive-round-one-results-2026-09-16.zh.md)。两行测的是不同工作，不能仅按数字大小判断哪个优化得更好。

QK 上一版保留原生 Norm 的兼容方案，三档耗时分别为 49.555、461.625、2,041.213 微秒；最新融合版明显更快。这个比较的对象是**上一版候选**，不是默认 compile。原生 eager 的另组对照也保留在修复报告中，比较对象均单独标明。

## 4. 两种 profiler 证实了什么

`torch.profiler`（PyTorch 性能分析器）和 `nsys`（NVIDIA Nsight Systems 系统分析工具）记录实际发射的 GPU kernel。本轮用它们核对融合是否发生，再用不带 profiler 的独立计时判断速度。

短序列的 kernel 数如下。QK 采用最新完整融合版，其余采用前述通过精度检查的候选。

| 算子 | 默认 compile：每次 kernel 数 | 候选：每次 kernel 数 |
|---|---:|---:|
| LayerNorm 加调制 | 1 | 1 |
| Gated Residual | 1 | 1 |
| RMSNorm | 1 | 1 |
| RoPE | 4 | 1 |
| QK Norm 加 RoPE | 精度未通过，不作有效对照 | 2 |
| Linear 加 GELU | 精度未通过，不作有效对照 | 2 |

最新 QK 的两份记录都包含 5 次调用、共 10 个 kernel，即每次两个。按每次调用累加 GPU kernel 执行时间，torch.profiler 为 13.383 微秒，nsys 为 13.351 微秒。它们与独立测得的 12.760 微秒采用不同计时条件，不能混进同一组速度评分。数据见[QK profiler 记录摘要](fused-precision-repair-2026-09-17.zh.md)。

Kernel 数通常能帮助解释发射开销，却不能单独证明加速。RoPE 从四个 kernel 合到一个，长序列仍然更慢；两类 Norm 的双方本来都是一个 kernel，收益也不能归因于减少发射次数。

nsys 早期因权限问题没有捕获到 CUDA 事件，后来改用软件跟踪，并按测量标记筛选。完整排障与当时的空报告记录保留在历史附件，未把空报告计作成功采集。

## 5. 这轮实验能怎样评价 Agent

**在当前测试范围内，Agent 能产出有用的 Norm 优化，也能根据具体反馈修复错误。** 但生成成功、精度通过、性能改善是三件事，需要分别验证。

本轮保留的失败包括：LayerNorm 初稿把补零位置错误计入方差；Linear 加 GELU 初稿调用了当前 Triton 不支持的接口；QK 初版在较大输入下精度失败；RoPE 的性能修订没有达到目标。这些记录见历史附件及精度排查报告，没有因最终修好而删除。

QK 最后的修复依赖笔者一侧的源码分析和归约探针，Agent 接收具体算法反馈后完成融合实现。因此，这组结果评价的是 **AutoKernel 提示策略与固定任务适配器在外部反馈下的表现**。完整原生 AutoKernel 自主搜索、多框架排名和真实模型收益尚未测得。

Linear 加 GELU 也有实现范围限制：候选保留原生 `F.linear`，只生成新的 GELU kernel，本轮没有生成新的矩阵乘法实现。

累计生成成本为 **11 次模型调用、约 21.5 分钟生成等待时间**，不含 GPU 评测和环境排障。构成为首轮 9 次，以及 QK 兼容修订、融合修订各一次；三阶段记录分别见历史附件、兼容修订报告和融合修复报告。这些时间不用于推算账单。

## 6. 测量条件与数据在哪

**精度与计时条件。** 硬件为单张 B300，物理 GPU 3。输入按固定随机种子生成，批大小为 1，每个 token 有 1,536 个特征；注意力头为 12 个、每头 128 个特征；线性层扩展维度为 8,960。主要输入采用 BF16，调制与门控参数使用 FP32，位置旋转沿用参考代码的 FP64 计算。这些都是固定算子测试，未加载真实模型中间特征。

默认基线为 `torch.compile(..., backend="inductor", mode="default", fullgraph=False)`，关闭矩阵乘法 TF32。环境为 Python 3.12.3、NVIDIA torch `2.12.0a0+0291f960b6.nv26.04.48445190`、CUDA 13.2、Triton 3.6、驱动 580.159.04。

普通正确性检查覆盖不同随机种子、重复输入、首个输入整体加 2 的压力用例。计时使用 CUDA Graph（记录后可重放的一组 GPU 操作）：预热后捕获 32 次调用，重放 50 次，每次总耗时除以 32，报告这些单次耗时的中位数。它减少了反复从 Python 发射操作的影响，不等于实际视频生成耗时，也不能把 50 次重放当成 50 次独立 Agent 实验。

**结果来源。** 表格来自已核对的终端输出，保留至小数点后三位。当前候选映射见[配置文件](../configs/candidates-r05.json)，输入生成与参照实现见[任务代码](../wanbench/tasks.py)。原始数据在实验机的 `experiments/wan/runs/` 下：

| 目录 | 对应数据 |
|---|---|
| `graph-scale-r01`、`graph-verify-r02` | 首轮中长序列、Norm 复测及 RoPE 修订 |
| `ffn-debug-r02`、`graph-debug-r01` | Linear 加 GELU 修订、其他短序列测量 |
| `qk-r03-graph`、`qk-r03-fresh` | 最新 QK 的原种子与新种子检查、计时 |
| `qk-r03-profiles` | 最新 QK 的 torch.profiler 与 nsys 记录 |
| `generate-*` | 候选源码、生成输入、响应及用量记录 |

GitHub 已保存评测代码、配置和报告；生成的候选源码、原始 JSON 与 trace（性能事件记录）仍在远端，尚未回传备份。读者目前可以查看评测实现与结果摘要，不能仅凭公开仓库完整重放全部候选实验。
